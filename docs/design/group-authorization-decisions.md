# 그룹 권한 · 오너십 개선 — 결정 요약

> 상태: **홀딩(작업 보류)** · 대상: `FlipNote-Group` 서비스 · 정리일: 2026-07-31
> 형식: 각 항목을 **문제 → 해결 방법 → 기댓값**으로 정리.
> 상세 스펙(매핑표·API별 게이팅·체크리스트)은 [`group-authorization-redesign.md`](./group-authorization-redesign.md) 참고.

## 1. 권한 모델: 동적 → 고정 전환

**문제**
그룹마다 각 role에 권한을 자유롭게 붙였다 뗐다 하는 동적 구조(`POST/DELETE /v1/groups/{id}/permissions`). 그룹마다 권한 조합이 달라질 수 있어 규칙이 불투명하고, 프론트가 "이 role이 뭘 할 수 있는지"를 예측할 수 없다.

**해결 방법**
role별 권한을 **코드로 고정**한다. 멤버의 role을 바꾸면 그 role에 정해진 권한을 자동으로 획득. 동적 부여/회수 API 2개는 폐기(또는 비활성).

**기댓값**
권한이 role만 보면 예측 가능해지고 일관성 확보. 프론트는 `GET /permissions`의 `permissions` 배열만으로 화면 게이팅 가능.

---

## 2. 그룹 정보 수정 권한 신설 (`GROUP_MANAGE`)

**문제**
현재 권한은 3개(`MEMBER_MANAGE`, `JOIN_REQUEST_MANAGE`, `INVITE`)뿐이라 "그룹 정보 수정"에 대응하는 권한이 없다. 서버는 `ChangeGroupService`에서 **OWNER 전용**으로 하드코딩돼 있는데, 문서엔 "OWNER or sufficient permission"이라 적혀 있어 코드와 불일치. 총괄매니저(HEAD_MANAGER)도 수정 가능하게 만들 방법이 없다.

**해결 방법**
`GROUP_MANAGE` 권한을 신규 추가하고 OWNER·HEAD_MANAGER에 매핑. `ChangeGroupService`를 OWNER 하드코딩 대신 `GROUP_MANAGE` 권한 체크로 변경.

**기댓값**
그룹 정보 수정을 권한 기반으로 게이팅. 프론트는 `permissions.includes("GROUP_MANAGE")`로 탭 노출. 문서-코드 불일치 해소.

---

## 3. 그룹 삭제: OWNER 전용 유지 (권한화하지 않음)

**문제**
그룹 삭제는 되돌릴 수 없는 파괴적 동작. 이를 일반 권한으로 만들면 하위 role에 실수로 새어나가 그룹이 통째로 삭제되는 사고가 날 수 있다.

**해결 방법**
삭제를 권한(permission) 목록에 넣지 않고 **OWNER 전용 특수 동작으로 유지**(현행 유지). OWNER 양도도 마찬가지로 권한이 아닌 특수 동작으로 취급.

**기댓값**
삭제 권한이 하위 role에 부여되는 실수 자체가 구조적으로 불가능. 가장 위험한 동작에 가장 높은 문턱 유지.

---

## 4. OWNER 양도 기능 신설

**문제**
OWNER를 다른 멤버에게 넘기는 경로가 코드상 전무. 역할 변경 API로도 OWNER 승격이 구조적으로 불가(`isHigherThan`의 `4 > 4 = false`). 그 결과 OWNER가 잠수하면 **아무도 승격 못 하고, 삭제도 못 하고, 나가지도 못해 그룹이 영구 잠김.**

**해결 방법**
OWNER 양도 전용 API 신규 추가(자발적). 대상 멤버를 OWNER로 승격하고 기존 OWNER는 한 단계 낮은 role로 강등. 역할 변경 API로는 불가하므로 별도 서비스로 구현.

**기댓값**
정상적인 인수인계가 가능해지고, 떠나기 전 양도로 잠수 문제의 1차 방어선 확보. 그룹당 OWNER는 항상 정확히 1명 유지.

---

## 5. 자발적 탈퇴 기능 신설

**문제**
본인이 그룹에서 나가는 기능이 없다(관리자에 의한 강퇴만 존재). 멤버가 스스로 이탈할 방법이 없고, 책임자가 나갈 때 인수인계 절차도 없다.

**해결 방법**
자발적 탈퇴 API 신규. role별로 흐름을 분리:
- **MEMBER**: 즉시 탈퇴
- **책임자(HEAD_MANAGER·MANAGER)**: 탈퇴 요청 → **OWNER 또는 요청자보다 상위 role**이 승인 → MEMBER로 강등 후 탈퇴
- **OWNER**: 탈퇴 불가. 반드시 OWNER 양도(§4)를 먼저 하고 나서 탈퇴

**기댓값**
사용자가 스스로 나갈 수 있고, 책임자 이탈 시 상위가 인지·인수인계할 여지 확보. OWNER 없는 그룹이 생기는 상황 방지.

**알려진 한계**
HEAD_MANAGER의 탈퇴는 상위가 OWNER뿐이라, OWNER 잠수 시 여전히 못 나감. 자동 승계(§6) 도입 전까지 남는 엣지 케이스로 수용.

---

## 6. (후속 과제) 잠수 자동 승계

**문제**
자발적 양도·탈퇴만으로는 OWNER가 완전히 잠수한 경우(아무 동작도 안 함)를 해결하지 못한다.

**해결 방법(예정)**
OWNER가 N일 이상 미접속이면 HEAD_MANAGER가 OWNER를 자동 승계. 단 "마지막 접속 시간" 추적 데이터가 필요.

**기댓값**
잠수 문제 완전 대비. 다만 신규 데이터 추적이 필요해 현 스코프에서 제외, **후속 과제로 분리.**

## 작업 방식 메모

- 원본 팀 repo(`FlipNoteTeam/FlipNote-Group`)는 건드리지 않고, **개인 fork에서 셀프 수정**. 백엔드 담당자와 별도 협의 없이 진행하며 **개인 포트폴리오 용도**.
- 서비스들은 각각 독립 repo(폴리레포). 이번 변경은 `FlipNote-Group` 한 곳에만 해당.
- 현재 **홀딩** 상태. 재개 시: fork 생성 → 로컬 remote를 fork로 재연결 → 브랜치 → §7(상세 문서) 열린 결정 확정 → 구현.

## 재개 전 확정해야 할 것 (상세 문서 §7)
1. role별 권한 고정 매핑 확정 (MANAGER에게 `MEMBER_MANAGE`/`GROUP_MANAGE` 부여 여부)
2. OWNER 양도 시 기존 OWNER의 강등 role (HEAD_MANAGER? MEMBER?)
3. 책임자 탈퇴를 승인제로 둘지 vs "즉시 탈퇴 + 알림"으로 단순화할지
4. 신규 엔드포인트 경로/네이밍
5. 자동 승계 후속 과제 편입 여부
