## 발견한 문제와 수정

| 문제 | 수정 |
|---|---|
| 문서 로딩 중 강퇴돼도 기존 입장 함수가 `sync`를 보내고 버퍼를 저장 | 소켓·카드셋별 세션 식별자로 입장 무효화, 버퍼 폐기, 비동기 작업 이후 재확인 |
| 매니저 조회와 Redis 등록 사이 강퇴 시 새 편집 세션이 살아남음 | 권한 조회 전에 입장 세션 등록, 강퇴 시 진행 중 입장도 취소 |
| 그룹 매니저 삭제 후 퇴장 실패 시 재전달에서 소켓 퇴장을 건너뜀 | 매니저 행 존재 여부와 무관하게 삭제와 소켓 철회 재실행 |
| Redis 사용자 인덱스 만료·누락 시 연결된 편집자를 찾지 못함 | 현재 서버의 소켓과 편집 세션 기준으로 철회 |
| 두 카드셋에 동시 입장하면 한 소켓의 버퍼가 섞임 | 소켓·카드셋별 입장 상태와 버퍼 분리 |
| 같은 ID의 다른 표기(`042`, `42`)가 철회 대상에서 빠짐 | 카드셋 ID 검증·정규화 |
| RabbitMQ 기본 이름의 연결을 두 번 초기화 | 반응·편집 권한 exchange를 공유 MessagingModule로 통합 |
| 매니저 삭제·카드셋 갱신이 교체 트랜잭션 밖에서 실행 | 조회·삭제·추가·갱신에 동일한 EntityManager 전달 |
| 메시지의 누락된 ID가 TypeORM 전체 조회·삭제 조건이 될 수 있음 | 메시지 종류·대상 ID·reason 검증 후 잘못된 메시지 폐기 |

Gateway의 `order: -1` 삭제는 원본 stash대로 유지한다. 기존 ChangeLog에 초기 polling 요청을 `ws://`로 전달해 연결이 실패했던 이력이 있다. HTTP 라우트가 polling을 처리하고, Spring Cloud Gateway의 WebsocketRoutingFilter가 Upgrade 요청을 WebSocket으로 전환하는 경로를 검증한다.

## 검증

- 수정 전 재현 스크립트: 일반 강퇴 후 편집 차단 1개 통과, 입장·버퍼·재전달·Redis 인덱스 누락 4개 실패. 수정 후 5개 모두 통과.
- Cardset: Jest 24개, Nest 빌드, TypeScript 검사, 변경한 TypeScript 파일 ESLint 통과.
- Group: 대상 userId 사용, 다른 그룹 멤버십 거부, 권한 거부, 삭제 실패 시 미발행, 커밋 이후 발행·롤백 시 미발행을 검증한다. 기존 컨텍스트 로딩 테스트를 포함한 전체 6개 통과.
- Group은 설치된 JDK 21에 임시 Gradle init script로 Java 17 `--release`를 지정해 검증했다. 저장소의 Java 17 toolchain 설정은 유지한다. JUnit Platform 활성화와 기존 테스트의 누락된 테스트 전용 설정도 보완했다.
- Gateway: 기본 라우팅 설정을 읽어 polling의 HTTP 유지와 Upgrade의 WebSocket 전환을 실제 WebsocketRoutingFilter로 검증했다. 기존 컨텍스트 테스트 포함 3개 통과.
- 실제 브라우저·Gateway·RabbitMQ·Redis를 함께 실행한 전체 편집 E2E 테스트는 수행하지 않았다.

## 적용 범위와 남은 한계

- 단일 Cardset 인스턴스 기준이다. 다중 replica 운영 전에는 모든 인스턴스에 권한 철회 이벤트를 전달해야 한다.
- DB 커밋과 MQ 발행 사이 이벤트 유실을 복구하는 outbox는 구현하지 않았다. 메시지가 정상 전달·소비된 시점에 활성 편집 세션을 철회한다. 그룹 강퇴 API의 204가 모든 소켓의 퇴장 완료를 보장하지 않는다.
- 이미 시작된 Redis 저장은 취소·롤백하지 않는다. 강퇴 시 대기 중인 버퍼, 진행 중인 입장의 후속 처리, 이후 편집 요청을 차단한다.
- 프론트엔드는 `kicked` 수신 시 해당 카드셋의 편집 UI와 Yjs provider를 정리해야 한다. 다른 카드셋용 Socket.IO 연결은 유지한다.
- 원래 작업 폴더의 스냅샷 실습 코드·문서와 원본 stash는 보존한다. 이 브랜치는 stash 기준점에서 분리했으므로 이후 awareness 사용자 정보 커밋(`11ab4dc`)은 병합 시 함께 확인한다.
